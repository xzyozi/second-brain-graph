# 設計ドキュメント作成・運用ガイドライン

本ディレクトリ (`docs/design/`) は、Second Brain OS の設計仕様書（基本設計、詳細設計、データ構造仕様）を管理・更新するための領域です。
新たな設計書を作成する際、および既存ドキュメントを保守する際は、以下のルールに従って運用してください。

---

## 1. ドキュメントの種類とテンプレートの選択

設計書を作成する際は、対象となるレイヤー・目的に応じて以下の3つのテンプレートの中から適切なものを選択してください。

| 設計書の種類 | 対象ドキュメント | 主な記述内容・用途 |
| :--- | :--- | :--- |
| **基本設計書** | `TEMPLATE_基本設計書.md` | システム全体の目的、アーキテクチャ方針、コンポーネント分離、システム境界、依存関係の定義 |
| **詳細設計書** | `TEMPLATE_詳細設計書.md` | 特定モジュール・関数の入出力パラメータ、状態遷移ルーティング、エラーハンドリング、単体テスト要件 |
| **データ構造仕様書** | `TEMPLATE_データ構造仕様書.md` | JSON/Pydantic等のスキーマ、状態タクソノミー、配置ディレクトリ、`fsync`+置換の原子性、FileLock排他制御 |

---

## 2. 執筆・記述に関する禁止事項と遵守ルール

### ① ドキュメントIDの不使用
* ドキュメント固有の固定ID（例: `SBOS-BD-001` 等）は使用せず、**標準的なドキュメント名および適用目的・作成意図** をメタデータテーブルに明記してください。

### ② ハイパーリンク（`file:///...` 等）の非依存
* ドキュメント内に URI 形式のハイパーリンクや特定のファイルパスリンクを直接埋め込まないでください。
* 関連ドキュメントの参照は、`SBOS-BD-002（基本設計書）` や `SBOS-DD-003（詳細設計書正本）` のように、**標準的な文書名テキスト**で記述してください。

### ③ 具象ソースコードの非掲載
* Python、Shell、Bash 等の具象プログラミングコードブロック（`def ...`, `import ...`, `uv run ...` 等）を直接掲載しないでください。
* コードの代わりに、**機能要件、入力・出力パラメータ表、型、バリデーション制約、事前条件・事後条件、失敗契約**をテキスト・テーブル・状態遷移表で記述してください。

### ④ 単一責任原則 (Single Source of Truth: SSOT)
* 特定コンポーネントのミクロな仕様（設定パラメータやエラー判定など）は、対応する詳細設計書またはデータ構造仕様書を正本として一元管理してください。
* 上位の設計書（基本設計書など）に同一の詳細仕様を重複掲載せず、正本となる詳細設計書名への参照に留めてください。

---

## 3. 新規ドキュメントの作成手順

1. 目的（全体構成 / モジュール制御 / データ構造）に合った `TEMPLATE_*.md` をコピーします。
2. ヘッダーのメタデータテーブル（ドキュメント名、改訂日、適用目的・利用意図）を記入します。
3. 規定の章立てに従って、コード・リンクを用いずに自然言語およびテーブルで仕様・契約を記述します。
4. 作成後、変更内容をリポジトリへコミットします。
