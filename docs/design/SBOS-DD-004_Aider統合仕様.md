## 1. 概要と基本方針

Aiderコンポーネントは、従来の自作マージロジックおよび自前のCoder Agentの役割を代替する実在OSSツールである。Gitのワーキングツリーに対して堅牢な差分適用・編集を担い、特定の実装言語、拡張子、テストディレクトリ構成を前提にしない。

編集対象は、Issue の Target Files、衛星 `project.json`、または `tools/coder_workflow.py` が検出する拡張子非依存のプロジェクトファイルから解決する。`.git`、仮想環境、`node_modules`、ビルド成果物などの生成・管理用ディレクトリは対象外とする。

> **既知の残課題:** 現行 `code_node` の実行戦略メッセージには `src/` と `tests/` の記述が残る。この記述は対象探索や品質ゲートの契約ではないが、言語・プロジェクト構成に依存しない指示テンプレートへ置換する必要がある。

## 2. Aider CLI 実行仕様 (`aider_runner.py`)

Aiderは非対話型のサブプロセスとして呼び出され、以下の起動オプションとパラメータによって安全に制御されます。

* **自動コミットの無効化:**
  * 実行時に必ず `--no-auto-commits`（複数形）オプションを付与します。
  * Aider自身にはファイルの修正のみを許可し、`git commit` 等のGit操作はLangGraphの `done_node` 側に完全に委譲・隔離します。

* **非対話バッチモード:**
  * プロンプトでの人間への確認要求をスキップするため、`--yes-always` オプションを付与してバッチ実行します。

* **並列実行競合防止（UUID一時ファイル）:**
  * Windows環境でのコマンドライン長制限（WinError 206）を回避しつつ、複数タスクの並列実行時のファイル上書き競合を防ぐため、Aiderへの指示内容は `uuid` を付与した一意のテンポラリファイル（`.aider.instruction_{uuid}.tmp`）経由で渡します。
  * 実行完了後や例外発生時は、`finally` ブロックで確実に一時ファイルを `unlink`（削除）するよう堅牢に実装されます。

* **新規ファイル作成の許可:**
  * 指定された `target_files` のパスがディスク上に存在しない場合、処理を中断せず警告ログ（`logger.warning`）を出力した上で、Aiderによる新規ファイルの自律生成を許可します。

## 3. モデル解決と環境変数・API制御

ローカルLLM環境（Ollama等）とシームレスに連携するため、Aider実行直前に以下の動的解決およびサニタイズ処理を実施します。

* **動的モデル解決 (`get_default_aider_model`):**
  * モデル名をハードコードせず、実行時に `config/models.json` などの設定プロファイル（`config.routes` 内の `aider_edit` または `code_edit`）から動的に解決します。
  * 選択されたバックエンドが `ollama` であり、かつモデル名にプレフィックスが無い場合は、自動的に `ollama/` を付与してAiderに渡します。

* **APIエンドポイントのサニタイズ:**
  * 環境変数 `OLLAMA_API_BASE` に `/v1` または `/v1/` のサフィックスが含まれている場合、Aider側の接続エラーを防ぐため、実行時の環境変数からこれを自動的に除去（サニタイズ）します。

## 4. LangGraph 統合とフェイルセーフ仕様 (`code_node`)

LangGraph上の `code_node` は、Aiderを呼び出すタスク実行ノードとして機能し、以下の仕様でプロンプト構築とエラーハンドリングを行います。

### 4.1 プロンプト（Instruction）の動的構築

Aiderへ渡す `--message` (指示内容) は、以下の3つの要素を結合して構築されます。

1. **初期指示:** Issue実装の基本指示（`instruction`）。
2. **実装計画:** `spec_draft_node` が生成した事前実装計画（`impl_plan`）。
3. **フィードバックループ:** プロジェクト宣言型の品質ゲート、CI Adapter（実装後）、Reviewer で失敗した際に正規化された出力や指摘を `aider_message` として蓄積する。

品質ゲートの失敗出力は、コマンド名・終了コード・標準出力または標準エラーを含める。CI の失敗出力は対象PRとチェック名を紐付け、認証情報を除去してから渡す。Aider は対象ファイルのスコープ制約を守り、失敗を解消する最小変更だけを行う。

### 4.2 エラー制御とリトライ遷移回路

Aiderの実行プロセスにおける異常系は、以下の通りLangGraphのステータスとして正規化され、安全に処理されます。

* **タイムアウト時のリトライ (LLM_TIMEOUT):**
  * プロセスタイムアウト等により `AiderRunError` が発生した場合は、`LLM_TIMEOUT` エラーとして分類します。
  * `llm_timeout_count` をインクリメントし、1回目のタイムアウト時は再度 `code_node` をリトライ（`retry_code`）します。
  * 2回連続でタイムアウトした場合は上限超過とみなし、即座に `FAILED_SYSTEM` へ遷移して安全停止します。

* **CLI異常終了 (SYSTEM_ERROR):**
  * Aiderが非ゼロの終了コード（`False`）を返した場合、リカバリ不能なシステム異常とみなし、再試行を行わずに `FAILED_SYSTEM` として処理を停止します。

* **データ欠損防止のフェイルセーフ:**
  * State 内に `target_files` キーが存在しない場合でも、`code_node` 側で KeyError を起こさず空リストに初期化し、異常停止を防ぎます（Aider による自律的なファイル抽出に委ねられます）。
