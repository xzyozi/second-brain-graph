# [TFG-0006] 暗号化・パスワード保護Officeドキュメントの自動判定・復号パース機構と構造例外処理の設計・実装

## 1. 概要・背景
grep検索エンジンにおいて、XLSXおよびDOCXファイルをパースし、テキストを検索対象に含める。暗号化またはパスワード保護されたファイルの場合は、暗号化ヘッダーを判別して復号処理を試行してからパースする。

## 2. 仕様および要求事項
- [ ] **暗号化シグネチャ判定**: ファイルのバイナリヘッダーをチェックし、標準 Zip 圧縮でないパスワード保護ドキュメントをパース前に判別する関数 `is_encrypted_office_file(file_path: str) -> bool` を実装すること。
- [ ] **復号およびパース処理**: パスワードが与えられた場合にメモリ上で復号してパースを行う処理を実装すること。
- [ ] **専用例外への集約**: パスワード不一致や復号不能なファイルが検出された場合、`EncryptedFileError` 例外を送出してエンジン側で安全にスキップ処理できる構造とすること。

## 3. 段階的実装手順 (Step-by-step Execution)
- **Phase 1 (Core Implementation)**: まず `src/` 配下の本体モジュール・主要ロジック・例外クラスのみを最小変更で優先実装すること。
- **Phase 2 (Test Implementation & Refinement)**: 本体実装完了後、`tests/` 配下の単体テストを作成・修正し、テスト通過を確認すること。

## 5. ドメイン知識・技術上の落とし穴 (Domain Knowledge & Technical Pitfalls)

### 使用ライブラリ・仕様
- `zipfile` (標準ライブラリ), `xml.etree.ElementTree` (標準ライブラリ), `msoffcrypto-tool`
- MS-OFFCRYPTO (Office Binary Document Password Structure) & ECMA-376 OpenXML 仕様

### 典型的な落とし穴 (Pitfalls)
- **暗号化判定のマジックバイト誤認**:
  標準の OOXML ドキュメント (docx/xlsx) は通常の Zip 圧縮のため先頭ヘッダーが `b"PK\x03\x04"` であるのに対し、暗号化・パスワード保護された Office ドキュメントは OLE2 複合ファイル構造 (`b"\xd0\xcf\x11\xe0"`) で保存され、内部に `EncryptedPackage` や `EncryptionInfo` ストリームを持つ。独自に `b"PK\x03\x01\x02"` などの架空のバイト列比較をしてはならない。
- **XLSX リレーションパス (`Target`) の二重プレフィックス問題**:
  `xl/_rels/workbook.xml.rels` 内の `Target` 属性値は、生成ソフトウェアやフォーマットによって `worksheets/sheet1.xml` (相対パス) と `xl/worksheets/sheet1.xml` (ルートからの相対パス) の両方の表記形式が存在する。一律に `f"xl/{r_target}"` と文字列結合すると `xl/xl/...` とパスが重複し、Zip 内アーカイブで `KeyError`（ファイルが存在しないエラー）となる。

### 推奨実装パターン (Recommended Patterns)
- **暗号化判定**: ファイル先頭の OLE2 マジックバイト (`b"\xd0\xcf\x11\xe0"`) の検出、および Zip エントリーの暗号化フラグ (`info.flag_bits & 0x1`) または `EncryptedPackage` バイト列の有無によって安全に識別すること。
- **Zip 内パス結合**: `xml_path = r_target if r_target.startswith("xl/") else f"xl/{r_target}"` のように、既に `xl/` プレフィックスが付与されているかチェックして動的に結合すること。

## 6. 設計制約・アンチパターンの禁止 (Architecture Constraints & Forbidden Actions)
安定した品質を維持するため、以下のアーキテクチャ原則を厳守すること：
- **単一責任と一方向のデータフロー**: 関数やクラス間で「相互呼び出し（循環依存・無限再帰）」となる設計を絶対に行わないこと。各機能は単一責任（SRP）を持たせ、処理結果は戻り値（またはストリーム等）として上位の呼び出し元に返し、制御フローを上位に委譲すること。
- **ハック的なフロー制御の禁止**: ループや再帰の停止条件として、不自然なフラグ変数（`is_first_time` 等）や深さカウンターなどの場当たり的な実装（ハック）を用いないこと。
- **堅牢な解析ロジック**: 外部データやファイル構造のパース処理において、特定の名前空間やマジックストリングのみを前提とした脆弱なハードコーディングを行わないこと。標準APIの安全な走査（ワイルドカードやイテレータ等）を利用すること。
- **既存の破壊禁止**: 無関係な設定ファイルやインターフェースを変更しないこと。既存の公開 API シグネチャを破壊しないこと。
