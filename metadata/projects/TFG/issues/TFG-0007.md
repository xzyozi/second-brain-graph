# [TFG-0007] マルチドキュメント一括検索の非同期・並列処理によるパフォーマンス強化

## 0. メタ情報 (Scope & Impact)
- **影響範囲**: サンドボックス限定（`src/grep/` 配下の検索ランナー・実行層の拡張）
- **既存コードへの依存**: あり（`src/grep/runner.py` や `src/grep/engine.py` 等の検索実行モジュール）
- **関連Issue**: なし

## 1. 概要・背景
多数のOfficeドキュメント（docx/xlsx/pptx）や大容量テキストファイルを単一スレッド・同期処理で順次パース・検索すると、XML解凍や文字列解析のCPU負荷により全体の検索時間が大幅に増大する。
本タスクでは、`concurrent.futures` (ProcessPoolExecutor / ThreadPoolExecutor) を活用してマルチドキュメントの一括検索・パース処理を並列化し、マルチコアCPU環境における検索スループットを劇的に向上させる。

## 2. 仕様および要求事項
- [ ] 複数ファイルの一括並列検索を行う `search_files_parallel(file_paths: list[str], pattern: str, max_workers: int = None)` 関数（またはクラスメソッド）を実装する。
- [ ] CPUバウンドなパース処理（Office XML解凍・パース）に適した `ProcessPoolExecutor`（またはファイル形式に応じたワーカー切り替え）を採用すること。
- [ ] `max_workers` パラメータで並列数を制御可能とし、未指定時は CPU コア数に応じた安全な上限を設定すること。
- [ ] 大量ファイル処理時にメモリを圧迫しないよう、`as_completed` 等を用いたストリーミング/ジェネレータ形式で検索結果を逐次取得・返却可能な設計とすること。
- [ ] ファイル権限エラー（`PermissionError`）や破損ファイル例外が発生した場合でも、全体の処理を中断させず、該当ファイルのエラー情報を結果オブジェクトに保持して並列処理を継続する耐障害性を確保すること。

## 3. 段階的実装手順 (Step-by-step Execution)
- **Phase 1 (Core Implementation)**: 
  - `src/grep/parallel_runner.py` を作成し、並列ワーカー関数および `search_files_parallel` のコアロジックを実装する。
  - ワーカー関数は `ProcessPoolExecutor` で安全に pickle 化できるよう、モジュールトップレベルに定義すること。
  - 個別エラー捕捉および結果集約イテレータを統合する。
- **Phase 2 (Test Implementation & Refinement)**: 
  - `tests/test_parallel_runner.py` を作成する。
  - 複数ファイルを対象とした並列検索テスト、一部ファイル破損時の継続処理テストを作成し、全テスト通過を確認する。

## 4. 編集対象ファイル (Target Files)
- `src/grep/parallel_runner.py`（新規作成）
- `src/grep/interface.py`（既存編集 / 並列検索用エントリーポイントの追加）
- `tests/test_parallel_runner.py`（新規作成）

## 5. ドメイン知識・技術上の落とし穴 (Domain Knowledge & Technical Pitfalls)
### 使用ライブラリ・仕様
- Python標準ライブラリ `concurrent.futures.ProcessPoolExecutor` / `ThreadPoolExecutor` を優先利用すること。

### 典型的な落とし穴 (Pitfalls)
- **ProcessPoolExecutor の Pickle エラー**: ワーカー関数にクラスのインスタンスメソッドやクロージャ（無名関数）を渡すと `Can't pickle local object` で実行時エラーになる。ワーカー関数および引数は必ずトップレベル定義の pickle 可能なデータ型に限定すること。
- **Windows 環境におけるマルチプロセス起動問題**: Windows の `multiprocessing` では子プロセスがメインモジュールを再インポートする。テスト実行時等で無限プロセス生成が発生しないよう適切な保護（`__name__ == '__main__'` 等）やエントリーポイント構造を意識すること。
- **メモリ消費量の過大化**: 大量ファイルの一括処理において全結果をメモリ上に保持すると OOM に繋がるため、`as_completed` やイテレータによるストリーミング処理を行うこと。

### 推奨実装パターン (Recommended Patterns)
- `GrepResult` オブジェクト（またはエラー情報を含む結果構造体）を返却するトップレベルワーカー関数 `_search_single_file_worker` を定義し、Executor 経由で呼び出す構成を推奨。

## 6. 設計制約・アンチパターンの禁止 (Architecture Constraints & Forbidden Actions)
- **共有状態の直接改変禁止**: ワーカープロセス間で共有オブジェクトの直接変更やスレッドセーフでない状態管理を行わないこと。
- **例外のサイレント無視の禁止**: 個別ファイルのパース失敗やアクセスエラーを無言で破棄せず、エラー情報付き結果として明示的に収集すること。
- **既存シグネチャの破壊禁止**: 既存の単一ファイル検索インターフェース（`search_file` 等）の引数・挙動を変更しないこと。

## 7. 対象外 (Non-Goals)
- Celery / Ray 等を用いた分散ネットワーク環境での並列検索（ローカルマルチコア処理に限定）。
- GPUアクセラレーション。

## 8. 完了定義 (Definition of Done)
- [ ] `search_files_parallel` により複数ファイルを並列でパース・検索できること。
- [ ] 一部ファイルが破損・読み込み不可の場合でも、他ファイルの検索が完了しエラー情報が結果に含まれること。
- [ ] 単体テスト（正常系・異常系・並列実行）がすべて通過すること。
- [ ] `ruff check` による静的解析エラーが一切ないこと。
